# OpenAI Intelligence Brief — 2026-10-04

## エグゼクティブサマリー

前回ブリーフ以降の最大の新規材料は **GPT-6 Sol / GPT-6 Luna** と **Dots** です。前者は日常的な業務・coding・computer useを、従来より低いcost per taskで処理する方向を強めています。後者は「常時稼働し、ユーザーに代わって継続的に仕事を進めるagent」というOpenAIの製品方向をより明確にしています。

同時に、直近の企業事例では Albertsons と Chatham Financial が、ChatGPT/Codex/APIを単なる個人 productivity tool ではなく、顧客体験・社内アプリ開発・業務プロセス再設計に組み込んでいます。

## 1. 何が変わったか

### GPT-6 Sol / Luna

**事実:** OpenAIはGPT-6 SolとLunaを公開しました。Solは複雑なprofessional workやcodingを主対象とし、Lunaはよりcost-efficientな日常処理を担います。OpenAI公開評価では、Solはcodingやcomputer-useを含む業務で前世代よりcost per taskを改善しています。

**分析:** enterpriseでは「最強モデルを全処理に使う」構成より、Lunaを大量・定型処理、Solを難しいreasoning/coding、Astraを最高難度へ振り分けるmodel routingが重要になります。

### Dots — always-on agents

**事実:** OpenAIはDotsを、ユーザーに代わって継続的に仕事を処理するalways-on agentとして発表しました。

**分析:** ChatGPTのagent化が「ユーザーが依頼して待つ」から「継続的に状態を持ち、必要な仕事を先回りして処理する」方向へ進んでいます。企業利用では、trigger・permission・approval・auditを人間の会話とは別レイヤーで設計する必要があります。

### Albertsons: ChatGPT Enterprise + API

**事実:** AlbertsonsはChatGPT EnterpriseとOpenAI APIの利用を拡大し、従業員の業務支援に加えて、basket building、repeat purchase、meal planningなど顧客向け体験にもAIを適用しています。

**分析:** enterprise AI導入が「社員向けChatGPT」と「顧客向けAPI application」を同じmodel ecosystemで展開する二層構造になっています。

### Chatham Financial: Codexでtrade validationを再設計

**事実:** Chatham FinancialはCodexとGPT-5.6を利用し、trade validationを30分から4分未満へ短縮したと報告しています。Codexは内部・顧客向けtoolの構築にも利用されています。

**分析:** coding agentの価値はdeveloper productivityだけでなく、domain expertとdeveloperが既存workflow自体を再実装する速度を上げる点にあります。

## 2. なぜ重要か

OpenAIのstackは、ChatGPT、Codex、API、Agents、computer use、persistent agentへ連続的になっています。企業側のarchitectureでは、AIを個別productとして選ぶより、

**Identity / policy → agent → model router → API/MCP/tools → sandbox/computer use → approval → audit**

として共通基盤化する方が再利用性が高くなります。

特にGPT-6 familyのcost/performance差が広がるほど、model routingはFinOpsの一部になります。

## 3. 具体的なユースケース

- Lunaで大量のclassification/extraction、Solで例外案件のreasoningを行う二段階処理。
- Codexがlegacy workflowを解析し、domain expertのレビューを受けながら内部toolへ置換。
- ChatGPT Enterpriseを社員向けknowledge/work layer、APIをcustomer-facing application layerとして共通化。
- always-on agentが定期的に案件・メール・project stateを確認し、必要時のみ人間へescalation。

## 4. 技術的な示唆・統合パターン

model selectionをapplication codeへ固定せず、task complexity、latency、risk、cost budgetを入力とするrouterとして切り出すべきです。

長時間agentでは、persistent stateとprompt cachingを組み合わせ、stable instructions/tool definitionsを再利用する構成が重要です。computer useはAPI/MCPが存在しない箇所へのfallbackとし、credentialとapproval boundaryを別管理するのが安全です。

## 5. 見落とされがちだが有用な機能

### GPT-6向けprompt caching改善

**何か:** GPT-6では、長時間agentが繰り返し送るinstructions、tool definitions、contextを再利用しやすくするprompt cachingが強化され、cached input tokenは最大90% discountになるとOpenAIは説明しています。

**なぜ見落とされやすいか:** model benchmarkや新agent productほど目立たず、architecture/cost optimizationの話として扱われるためです。

**解決する問題:** 長時間agentでは毎turn巨大なsystem/context/tool schemaを送るため、cache hit率が低いとcostとlatencyが急増します。

**誰に有用か:** AI platform team、backend engineer、FinOps、agent developer。

**利用例:** 共通instructionとtool schemaをstable prefixへ置き、conversation固有contextを後段に配置してcache reuseを最大化する。

### Agent Builder / Evals終了への移行期限

**何か:** OpenAIはAgent BuilderとEvals productを2026年11月30日以降利用不可とし、code-based workflowにはAgents SDK、natural-language型にはWorkspace Agentsを推奨しています。

**なぜ見落とされやすいか:** 新機能ではなく既存productのmigration noticeだからです。

**解決する問題:** 年末直前に既存agent/evaluation workflowが停止するmigration riskを避けられます。

**誰に有用か:** OpenAI platform owner、AI CoE、agent developer。

**利用例:** Agent Builderで運用中のworkflow inventoryを作り、11月前にAgents SDKまたはWorkspace Agentsへ移行する。
